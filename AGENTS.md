# AGENTS.md

## Project overview
This repo is a Node.js (ESM) toolchain for generating and packaging S.T.A.L.K.E.R. 2 mod configuration files and assets. Most logic lives in `.mts` scripts under `src/` and is run via `node` directly (no build step).

## Local requirements
- Node.js 24+ (needs `.mts` loader support).
- STALKER2ZoneKit (official SDK) installed locally.
- Optional tooling for packaging and publishing:
  - `repak` for quick `.pak` rebuilds.
  - SteamCMD for Steam Workshop publishing.

## Environment variables
Copy `.env.sample` to `.env` and fill paths/secrets. Common vars:
- `SDK_PATH`: STALKER2ZoneKit root path.
- `STALKER2_FOLDER`: game install path.
- `REPAK_PATH`: path to `repak` binary.
- `STEAMCMD_PATH`, `STEAM_USER`, `STEAM_PASS`: Steam publish credentials.
- `MODIO_API`, `MODIO_API_SECRET`: mod.io publish credentials.
- `NODE_PATH`: optional path to a Node.js 24+ executable. External TypeScript loaders are not supported.
- `NEXUSMODS_API_KEY`, `NEXUSMODS_CATEGORY_ID`: Nexus Mods publishing.
- `ALLOW_MERGED_STRUCTS`, `DRY`: optional behavior flags.

## Repo layout
- `src/`: all scripts and utilities (TypeScript `.mts` + a few `.ts`).
- `Mods/`: mod source/config payloads (project-specific content).
- `DLCGameData/`: extracted or staged DLC game data (generated or synced). Mirrors the in-game
  `Stalker2/Content/GameLite/DLCGameData` layout; transformers opt in with `transformer.dlc = true`.
- `GameLite/`: staged lightweight game data copy (generated).
- `DesignDocs/`: docs/specs for mods and workflows; treat as the canonical spec location for gameplay/system notes.
- `.env.sample`: environment template.
- `.l1*.cache.zlib`: local caches (ignored by git).

## Key scripts (package.json)
Run with `node` via npm scripts:
- `npm run prepare-configs`: core pipeline to generate config files.
- `npm run pack-inject`: package + inject into game content.
- `npm run cook-inject`: cook assets and inject into game.
- `npm run publish-steam`: publish to Steam Workshop.
- `npm run publish-modio`: publish to mod.io.
- `npm run update-readme`: regenerate mod readme files.
- `npm run push-to-sdk`: push content into SDK project.
- `npm run pull-staged`: pull staged assets into repo.
- `npm run pull-assets`: pull game assets into staging.
- `npm run repack-republish-all`: batch cook/inject for all mods.
- `npm run create-mod -- <ModName> ...`: scaffold a new mod (see `src/create-mod.mts`).
- `npm run purge-caches`: remove `.cache.zlib` files (safe cleanup).
- `npm run check-comments`: list new mod.io + Steam Workshop comments on all published mods (`--mark-seen` to acknowledge; see the `mod-comments` skill).
- `npm run voiceover-server`: voice-line review site. The whole voiceover workflow (Higgs TTS pipeline, review site, agent) is in `src/voiceover/README.md`.

## Generated/ignored content
The following are git-ignored and should not be committed unless explicitly requested:
- `node_modules/`, `.env`, `GameLite/`, `DLCGameData/`, `sdk/`, `.modio/`, `.nexusmods/`.
- Autogenerated files `raw/`, `steamworkshop/`
- Cache files: `.l1.cache.zlib`, `.l2.cache.zlib`, `.l3.cache.zlib`, `.l1.type-gen.cache.zlib`.
- `types.mts`, `*.zip`, workshop VDF files.

## Development notes
- Scripts are ESM and `.mts`; follow the existing import style and path conventions.
- When running `.mts` directly under modern Node with native type stripping, use `import type` for type-only imports from local modules. A plain `import { Foo }` will still be treated as a runtime export request and can fail on Node 24+ if `Foo` is type-only.
- Use native Node.js 24+ for `.mts` scripts. The installed `s2cfgtojson` 9.0.1 ships compiled JavaScript. Do not use `NODE_TS_TRANSFORMER` or the IntelliJ/JetBrains tsx loader: it caused recursive esbuild spawning and exhausted memory on 2026-10-07. `src/ensure-env.mts` rejects legacy loader configuration. If a command stalls, inspect its process tree and stop surviving children before retrying.
- Prefer `rg` for searching and avoid wide refactors unless asked.
- When touching scripts that integrate external tools (SDK, SteamCMD, repak), keep path/credential handling intact.
- Many scripts read from environment variables; do not hardcode local paths.
- `SDK_PATH` is expected to point at the STALKER2ZoneKit root; cfg source data is under `Stalker2/Content/GameLite` (see `src/base-paths.mts`).
- For opening files in IntelliJ at a specific line, use: `"$IDEA_PATH" --line <line> <path-to-file>` (set `IDEA_PATH` in `.env`).
- To run `.mts` scripts manually, use Node.js 24+ directly (for example `node ./src/quest-nodes-to-js.mts`). If using the executable from `.env`, use `PATH="$(dirname "$NODE_PATH"):$PATH" "$NODE_PATH" ./src/quest-nodes-to-js.mts`; no `--import` or `--loader` is needed.

## How to analyze `.cfg` files
- Source of truth is the SDK GameLite tree at `SDK_PATH/Stalker2/Content/GameLite` (this is what `src/base-paths.mts` calls `baseCfgDir`).
- Use `s2cfgtojson/types.mts` for up-to-date typescript types for parsed cfgs.
- Schema reference lives in `node_modules/s2cfgtojson/types.mts`; consult it to confirm field names, optionality, and nested struct shapes.
- Use the existing loaders instead of ad‑hoc parsing:
  - `src/get-cfg-files.mts` to scan and cache file lists.
  - `src/read-file-and-get-structs.mts` to parse a file into typed `Struct` objects.
  - `s2cfgtojson` types (imported across `src/`) define the schema for most prototypes.
- Prefer `node` scripts over manual edits when inspecting or transforming cfgs; most scripts assume ESM and the GameLite base path.
- Keep `.cfg` analysis read‑only unless explicitly asked to generate patch files via `src/get-cfg-file-processor.mts`.

## How to create `.cfg` mods
- Scaffold with `npm run create-mod -- <ModName> --files "<cfg>[,<cfg>]" [--files ...] [--description "..."] [--prepare]` (see the `eng-project-setup` skill). It writes `package.json`, `meta.mts`, one `transform<File>.mts` stub per `--files` flag and the icon; `--prepare` regenerates `raw/` with `SKIP_SDK_PUSH=1`. Stay on `master`; no branch is needed.
- Define one or more struct transformers; follow the pattern in `Mods/NoFallDamage/meta.mts` and `Mods/NoQuestCooldown/meta.mts`.
- Try to name struct transformers as `transform%File%Prototypes` (for example, `transformWeaponGeneralSetupPrototypes`) so file intent is obvious from the function name.
- Always set `transformer.files` to the exact cfg paths you intend to patch (paths are relative to `GameData/` and usually start with `/`). You can also use substring pattern, similar to `Mods/MasterMod/transformQuestNodePrototypes.mts`.
- Do not use multiple transformers to modify the same target cfg file. If one cfg needs several behaviors (edits + injected structs, etc.), combine them inside a single transformer and split the implementation into helper functions/methods.
- Use `struct.fork()` to create a patched bare minimum copy. Use `struct.fork(true)` to create a deep copy. When changing nested structs, set `__internal__.bpatch = true` on the nested struct.
- `bpatch` only adds/replaces properties on the current struct and its nested patched children; it does not remove omitted siblings by itself. To remove a nested struct or array entry, call `fork.removeNode(key)` on a bpatch struct (emits `{removenode}`; on a plain value it assigns `empty`). Alternatively, to replace a whole nested struct such as `Launchers`, emit that field as a non-`bpatch` struct rather than a partial `bpatch` container.
- `PreinstalledAttachmentsItemPrototypeSIDs`: never bpatch a single entry. A partial `{bpatch}` list replaced
  the shipped one in game and stripped the guns' hidden built-in magazines and silencers (X16Scopes,
  2026-10-22). Re-emit the whole list without bpatch, keeping the vanilla `bskipref` and cloning every
  other entry (MasterMod's `stripDefaultScopes` does the same).
- s2cfgtojson 9.1.0 renders a `refkey` (or nested key) that starts with digits as an array index: a GUID
  `38475DEF...` becomes `refkey=[38475]` (`isNumber` uses `parseInt`). To copy a GUID-keyed struct
  (SpawnActorPrototypes), emit a full `clone()` without `refkey` (LairTiers, 2026-10-23).
- For adding new structs, clone/backfill, set `__internal__.isRoot = true`, and return them from the transformer (see `Mods/HeadlessArmors/meta.mts`).
- If a mod must patch prototypes introduced by another mod and those raw/generated structs are not available during `npm run prepare-configs`, assume the target SIDs exist and inject one-shot patch structs with a `let once = false` guard. It is OK to depend on TypeScript source objects/constants (for example SID definition arrays), but not on the other mod's generated/raw structs.
- To branch quest logic on whether another mod is installed, follow `DesignDocs/DetectInstalledModSpec.md`: the provider adds a permanent `<Mod>Installed` flag effect and a `ModWorldSubsystem` blueprint that applies it with `XApplyEffectOnPlayer` on world load (registered through an `Autogenerated_<n>_WorldSubsystemData` asset, which `src/world-subsystem-data.mts` regenerates on every pull), and the consumer checks it with an `If` `Effect` condition on the player. Every mod is a provider: `src/announce-installed.mts` adds the effect and the renamed blueprint on `prepare-configs` (excluded mods in `NOT_ANNOUNCED`), which turns a cfg-only mod into a split mod that needs `cook-inject`.
- To run a console command on every world load (quest logic for saves made before the mod was installed, for
  example), set `gameStartCommand` in the mod's `meta.mts`; its announce blueprint runs it after the flag
  (`XStartQuestNodeBySID <node>` starts a quest node). One shared template, never a second blueprint or a
  per-mod edit: change the graph in any mod's copy, then `src/refresh-announce-template.mts` (see the spec).
- Textures for import must be 8-bit PNGs. The editor imports a 16-bit PNG as a linear 16-bit texture and
  shows the art washed out (silver where it should be near-black); ImageMagick's `xc:` canvas makes 16-bit
  output unless written with `-depth 8` (X16Scopes icons, 2026-10-23).
- Some vanilla Niagara systems don't compile in the Mod Editor out of the box: the FullEditor pak lacks
  some GSC module scripts (e.g. `IronWind/Niagara/NMS_Camera_Spikes`), and one missing script cascades into
  hundreds of errors. Delete the module that calls it (the greyed-out `NMS Camera ...` rows in
  `NS_IronWind_Loop`) and recompile (VisibleRazorAnomaly, 2026-10-24).
- A string typed into a blueprint node pin is compiled into its bytecode: patch it only with a same-length
  byte swap (pad with spaces), never with `replaceExportStrings`.
- Keep edits in transformers and regenerate `raw/` via `npm run prepare-configs`; do not hand-edit `raw/` unless explicitly asked.
- Voiced dialogs: see the `eng-dialog-voiceover` skill. Mods must be installed under `Content/Paks/~mods/` (other
  folders mount as plain paks, and the game never registers the mod's assets by class, e.g. its voice data), and every
  TextTool speaker must be a known character (Skif is `PC`), or the editor drops that line's voice at cook.
- A mod's named NPC: its own ObjPrototype (`NPCPrototypeSID`, `CustomMeshGeneratorPrototypeSID` for a fixed look, as
  vanilla's Sultan) and NPCPrototype (`NameTextKey`, inheriting `[0]` like every vanilla named NPC). Never reuse a
  spawn actor GUID that has already spawned something else: WolfArmorFetch's Bagor kept coming back as a generic
  bandit from his old GUID until it was replaced, while a console spawn of his prototype was named (2026-10-25).
  His TextTool speaker must be a character the editor knows (`textToolCharacter` in `Mods/WolfArmorFetch/dialog.mts`),
  or his voice is dropped at cook.
- An `End` node with `ExcludeAllNodesInContainer = true` excludes every node of its quest, and an excluded `Spawn`
  node despawns what it spawned (every `SpawnNodeExcludeType` does). A quest that spawns a reward (a stash, a
  body) must not End afterwards: vanilla's stash quests (EQ155_P) have no End. WolfArmorFetch's Falcon stash
  vanished this way on 2026-10-20.
- Reward stashes: spawn a stash actor of the mod's own (`SpawnOnStart = false`). Vanilla world stashes are also
  spawned or revealed by other systems and mods (StashClueRework turns their spawn on start off).
- Quest conditions that must all hold go in separate groups: `Conditions { [0] { [0] = A } [1] { [0] = B }
  ConditionCheckType = And }`, as vanilla does. Conditions sharing one group are not ANDed, and
  `getConditions` in `src/struct-utils.mts` puts every condition in group `[0]`; LairTiers' multi-condition
  `If`s passed on any single condition (2026-10-24). Use it only for one condition.
- Keep running quests small: a running quest costs game-thread time per node. One always-on quest of
  ~14,000 nodes, and a 4,100-node quest left running, each dropped the game to a few fps (LairTiers,
  2026-10-24). Put bulk work in quests started on demand that finish with a vanilla `End` node; a
  `ConsoleCommand` `XEndQuestBySID` from inside the quest did not end it.
- To check "does this NPC exist yet", use an `IsCreated` condition on its GUID (`TargetPlaceholder`). A
  `Bridge` condition on a vanilla `OnNPCCreateEvent`/`Technical` node came out False on a save long past
  it, so WolfArmorFetch's world-load re-attach never ran (2026-10-25). Don't chain off a `Spawn` node's
  output either: launch follow-ups from the spawn's own launchers. A node launched by `SpawnHook` never
  ran on a save that did spawn him (WolfArmorFetch Cover, 2026-10-25).
- `SKIP_SDK_PUSH=1 prepare-configs` leaves the SDK's cfg copies stale, and a later publish/cook-inject
  still repacks from the SDK: its fingerprint is taken from `raw/`, so it ships the old cfgs without
  noticing. Before any publish or inject, run a plain `prepare-configs` (WolfArmorFetch, 2026-10-25).
- `ShowFadeScreen` quest nodes can be used as a lightweight in-game debug message display during quest logic prototyping.
- In quest-node chains, `ItemRemove` on an absent inventory item appears to attempt removal without failing the chain (verified in DecoupledRanks work); do not assume it hard-fails unless observed otherwise for a specific node type/case.
- Validate references against GameLite: `ItemPrototypeSID`, `UpgradePrototypeSIDs`, `EffectPrototypeSIDs`, `MeshGeneratorPrototypeSID`. Avoid duplicate UpgradePrototypeSIDs.
- In special cases when mod requires SDK involvement and doesn't modify cfgs, `structTransformers` can be empty (see `Mods/NoEnemyMarkers`).

## Design docs (specs)
- Store new system or gameplay specs in `DesignDocs/` and keep them aligned with GameLite cfgs and `s2cfgtojson` schemas.
- When writing or updating a spec, document: source cfg path(s), field semantics, observed ranges/quirks, and any known anomalies.
- Avoid enumerating large SID lists in specs unless explicitly requested; focus on logic and structure.

## Typical workflows
- **Switch to a working branch**: each git branch points to `master`, scripts pick up current mod name from git branch name.
- **Generate configs**: `npm run prepare-configs` after updating mod data in `Mods/`.
- **Inject into game**: `npm run pack-inject` (fast, cfg-only mods, will break on assets-mods) or `npm run cook-inject` (full cook).
- **Publish**: set `.env` credentials, then `npm run publish-steam` or `npm run publish-modio`.
- **Sync assets**: `npm run pull-assets` or `npm run pull-staged`.

- Cook timing: measure the current run with shell `time` and timestamped UAT `Log.json`; do not use old 21–22 min/pass comments as current estimates. X16Scopes full two-pass asset cook on 2026-10-07 took 6m 26.649s. See `DesignDocs/CookSpeedupLearnings.md` for context; cache state and mod content affect duration.

## Testing
No dedicated test command is defined. Test by running `npm run prepare-configs`.

## Safety
- Do not remove local caches or staging directories unless explicitly requested; prefer `npm run purge-caches` for cleanup.
- Avoid destructive git actions unless the user asks.
- If scripts modify local SDK/game paths, confirm expected targets before running.

## Public-facing text: no spoilers
Players read mod titles, descriptions, readmes, changenotes and commit messages (the repo is public and
publish descriptions link to it). Keep them spoiler-free:
- Don't name the items, rewards, quest or job names, characters' plans or plot points a mod adds.
- No exact numbers that give content away, such as durability, prices or reward amounts.
- Describe at the level of "a new job from Wolf", "a different reward when HeadlessArmors is installed".
- Changenotes: one short sentence covering the release (see `changenote` in `Mods/<Mod>/meta.mts`).
- A changenote describes one concrete release, never a running total. Before writing it, find the last
  published version (`git log -1 --grep="publish: <Mod>"`) and read the changenote in that commit
  (`git show <hash>:Mods/<Mod>/meta.mts`). Whatever it already said has shipped: drop it, and write
  only what changed since that commit (`git diff <hash> -- Mods/<Mod>`). If the current changenote
  still matches the published one, replace it entirely.
- Commit messages describe the mechanism (transformers, nodes, flags) without retelling the story.
- Code comments, DesignDocs and in-game text are exempt.
